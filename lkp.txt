A. IDENTIFIKASI KARAKTERISTIK ARSITEKTUR
=====================================================================

1. Kualitas Non-Fungsional (Architectural Characteristics)

a) Performance
- Halaman harus dimuat cepat di koneksi normal karena website bersifat informasi publik.
- Pendekatan: HTML/CSS/JS murni tanpa framework berat untuk menekan ukuran aset.

b) Scalability
- Versi awal fokus pada skala kecil-menengah (traffic restoran lokal).
- Arsitektur tetap disusun modular agar mudah ditambah backend/API pada fase lanjutan.

c) Availability
- Website harus tersedia kapan pun pelanggan mencari menu/jam buka/reservasi.
- Solusi saat ini berbasis frontend statis, sehingga deployment sederhana dan stabil.

d) Security
- Pada versi saat ini, data reservasi hanya validasi client-side dan simulasi submit.
- Risiko yang perlu diantisipasi pada fase lanjutan: validasi server-side, sanitasi input, proteksi spam form.

e) Usability
- Navigasi jelas (Beranda, Menu, Reservasi, Kontak).
- Fitur menu memiliki filter kategori, tab, dan pencarian agar pengguna cepat menemukan item.

f) Accessibility
- Menggunakan semantic HTML, label input, dan aria-live untuk notifikasi form.
- Target kontras warna dan fokus keyboard memenuhi praktik WCAG dasar.

g) Maintainability
- Struktur proyek dipisah per concern: halaman HTML, style global, script global.
- Versi WordPress disediakan untuk memudahkan manajemen konten menu oleh admin non-teknis.


2. Batasan Arsitektur (Constraints)

- Teknologi wajib awal: HTML, CSS, JavaScript vanilla (tanpa framework frontend).
- Tidak ada integrasi third-party (payment, maps SDK, analytics) pada fase ini.
- Aset harus lokal (gambar/icon lokal).
- Sistem harus tetap nyaman di laptop (>=1366px) dan responsif hingga 1024px.
- Form reservasi belum terhubung backend/database pada implementasi awal.


3. Kebutuhan Bisnis/Fungsional Paling Kritis

- Menampilkan identitas restoran dan informasi operasional dengan jelas.
- Menyediakan katalog menu yang mudah dijelajahi.
- Menyediakan alur reservasi sederhana agar calon pelanggan bisa mengirim permintaan booking.
- Menyediakan data kontak cepat (telepon, WhatsApp, email, alamat, jam buka).

B. IDENTIFIKASI LOGICAL COMPONENT
=====================================================================

1. Presentation Layer (Frontend UI)
- Komponen: Navbar, Hero, Shortcut Card, Menu Grid, Reservation Form, Contact Card, Footer.
- Tanggung jawab: menampilkan UI, menerima input pengguna, dan menampilkan feedback.

2. Client Interaction Layer (JavaScript)
- Komponen: MenuFilterController, SearchController, ReservationFormController, NavStateController.
- Tanggung jawab: logika interaksi di browser (filter, pencarian, validasi, notifikasi sukses).

3. Content/Data Layer (Current Static)
- Komponen: file HTML + atribut data pada menu card.
- Tanggung jawab: menyimpan konten menu/kontak dalam bentuk statis.

4. Content Management Layer (WordPress Theme Version)
- Komponen: Custom Post Type menu_item, taxonomy menu_category, template pages, meta box admin.
- Tanggung jawab: manajemen data menu dari dashboard WordPress.

5. Future Service Layer (Planned)
- Komponen rencana: Reservation API + Database.
- Tanggung jawab: menyimpan reservasi, konfirmasi otomatis, dan pelaporan operasional.

C. PEMILIHAN ARCHITECTURAL PATTERN
=====================================================================

Pattern terpilih: MODULAR MONOLITH (dengan struktur layered sederhana).

1. Alasan pattern paling cocok
- Scope proyek saat ini masih fokus fitur inti restoran, sehingga satu codebase lebih efisien.
- Tim dapat bergerak cepat untuk iterasi UI/UX tanpa kompleksitas distributed system.
- Mudah dipelihara untuk kebutuhan akademik dan implementasi awal bisnis.
- Sudah menyiapkan modularitas (UI, logic, content) sehingga transisi ke backend tetap memungkinkan.

2. Trade-off negatif yang perlu dipertimbangkan
- Batas skalabilitas vertikal lebih cepat tercapai dibanding microservices.
- Deploy tetap satu unit besar; perubahan kecil tetap ikut siklus rilis keseluruhan.
- Isolasi kegagalan antar modul tidak sebaik arsitektur layanan terpisah.

3. Kesesuaian pattern dengan architectural drivers
- Performance: aplikasi ringan, tanpa overhead komunikasi antarlayanan.
- Maintainability: struktur modular dalam satu repositori memudahkan pemahaman.
- Usability: perubahan UI cepat diimplementasikan karena stack sederhana.
- Cost/Time-to-market: biaya implementasi rendah, sesuai kebutuhan proyek awal.

D. ARCHITECTURE DECISION RECORD (ADR)
=====================================================================

ADR-001: Memilih stack frontend vanilla (HTML/CSS/JS)
- Status: Accepted
- Context: Proyek tahap awal membutuhkan implementasi cepat, ringan, mudah dipahami.
- Decision: Menggunakan HTML5, CSS3, JavaScript tanpa framework.
- Consequences:
	Positif: performa baik, dependency minim, mudah dipelajari.
	Negatif: skalabilitas code frontend jangka panjang perlu disiplin struktur.

ADR-002: Memilih pattern Modular Monolith
- Status: Accepted
- Context: Fitur masih dalam domain tunggal restoran dengan kompleksitas moderat.
- Decision: Menyusun arsitektur modular dalam satu aplikasi/repository.
- Consequences:
	Positif: delivery cepat, deployment sederhana.
	Negatif: scaling horizontal terbatas jika trafik naik drastis.

ADR-003: Reservasi fase awal bersifat simulasi client-side
- Status: Accepted (Temporary)
- Context: Fokus praktikum saat ini pada UI/arsitektur, belum pada backend produksi.
- Decision: Submit reservasi divalidasi di browser dan ditampilkan notifikasi sukses.
- Consequences:
	Positif: demo alur user selesai lebih cepat.
	Negatif: data belum persisten, belum siap untuk operasional penuh.

ADR-004: Menyiapkan jalur migrasi ke WordPress Theme
- Status: Accepted
- Context: Pemilik restoran membutuhkan pengelolaan menu yang mudah oleh admin non-programmer.
- Decision: Menyediakan versi theme WordPress dengan CPT menu_item + taxonomy menu_category.
- Consequences:
	Positif: konten menu dapat dikelola dari dashboard.
	Negatif: perlu perhatian tambahan untuk sinkronisasi style/fitur antara versi statis dan WP.
